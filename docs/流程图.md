## 图 1：用户使用流程（主闭环）

对应作业要求点名的：**发布信息 → 浏览 / 搜索 → 查看详情 → 联系发布者 → 更新状态**。

```mermaid
flowchart TD
    Start([打开首页 index.html]) --> List[浏览信息卡片列表]
    List --> Filter{想怎么找?}
    Filter -->|按类型/分类/地点/状态| Facet[四维筛选<br/>每个选项显示条数]
    Filter -->|知道关键词| Search[搜索页 search.html<br/>热门词 / 历史 / 命中高亮]
    Facet --> List2[筛选后的列表]
    Search --> List2
    List2 --> Detail[详情页 detail.html]

    Detail --> NeedVerify{这条招领<br/>需要认领验证吗?}
    NeedVerify -->|否 · 寻物信息| Contact[联系方式直接可见]
    NeedVerify -->|否 · 「其他」类信任模式| Contact
    NeedVerify -->|是| Locked[🔒 联系方式已锁定<br/>显示题数与剩余次数]
    Locked --> Verify[认领验证答题页 verify.html]
    Verify --> Result[结果页 verify-result.html]

    Contact --> Copy[一键复制联系方式]
    Result -->|通过| Copy
    Result -->|3 次全败| Appeal[申诉页 appeal.html<br/>人工审核通道]

    Copy --> Offline[线下交接 / 核对]
    Appeal --> Owner[发布者在「我的」处理申诉]
    Owner -->|同意交还| Offline

    Offline --> Done{发布者标记状态}
    Done -->|寻物| Found[已找到]
    Done -->|招领| Returned[已归还]
    Found --> Grey[列表置灰 + 沉底<br/>详情页不再显示联系入口]
    Returned --> Grey
    Grey --> End([闭环结束])

    List -.->|没找到| Publish[发布页 publish.html]
    Detail -.->|没找到| Publish
    Publish --> Success[发布成功页 success.html<br/>编号 + 智能配对推荐]
    Success --> List
    Publish -->|发布者身份| Mine[我的 mine.html]
    Grey --> Mine
```

## 图 2：数据流与分层

一条最关键的设计：**数据层向上返回的每一个对象都经过 `toPublic()`，验证题的正确答案在这一步被剥离，认领记录与申诉明细同样不外传。** 首页、搜索结果、详情页、答题页拿到的数据里根本不存在正确答案——不是靠界面藏起来，而是数据压根没传出来。

```mermaid
flowchart TB
    subgraph View["① 页面层（只管结构）"]
        HTML["9 个 HTML"]
    end

    subgraph Ctrl["② 控制器层（收集输入 / 渲染结果）"]
        PI[page-index.js] --- PS[page-search.js] --- PP[page-publish.js]
        PD[page-detail.js] --- PV[page-verify.js] --- PM[page-mine.js]
        PA[page-appeal.js] --- PVR[page-verify-result.js] --- PSU[page-success.js]
    end

    subgraph UI["③ 公共界面层"]
        UIJS["ui.js<br/>导航外壳 / 卡片渲染 / 轻提示 / 确认框 / 一键复制"]
    end

    subgraph Data["④ 数据层 ★ 全部业务规则"]
        ST["store.js<br/>校验 · 增删改查 · 搜索筛选排序 · 状态流转<br/>认领验证 · 申诉 · 老数据迁移"]
    end

    subgraph Base["⑤ 基础层"]
        CFG["config.js<br/>业务字典"]
        UTIL["utils.js<br/>纯函数"]
        SEED["seed.js<br/>演示数据"]
    end

    subgraph Store2["⑥ 存储适配器（可注入）"]
        LSA["localStorage"]
        SSA["sessionStorage"]
        MEM["内存"]
    end

    HTML --> Ctrl
    Ctrl --> UIJS
    Ctrl --> Data
    UIJS --> Data
    Data --> Base
    Data --> Store2
    LSA -.降级.-> SSA -.降级.-> MEM

    Data -->|"toPublic() 出口"| OUT["公开视图<br/>✅ 题干与选项<br/>❌ 无 answer<br/>❌ 无 claims / appeals<br/>❌ 未解锁则无 contactWay<br/>✅ 姓名打码 张**"]
    OUT --> Ctrl

    LSA -.->|"file:// 下 Chrome 视为同一来源，<br/>页面之间能共享数据"| LSA
```

## 图 3：信息状态流转

状态字段只有 `active / done` 两个取值，**状态文案由「类型 × 状态」两两组合推导**，界面层只认 `LF.statusTextOf()`，避免文案散落各处。

```mermaid
stateDiagram-v2
    [*] --> 进行中: 发布信息

    state "进行中 (active)" as A {
        state "寻物 · 寻找中" as L
        state "招领 · 待认领" as F
    }

    A --> B: 发布者标记已完成<br/>markDone()
    B --> A: 发布者恢复为进行中<br/>restorePost()

    state "已完成 (done)" as B {
        state "寻物 · 已找到 (doneType=found)" as L2
        state "招领 · 已归还 (doneType=returned)" as F2
    }

    B --> [*]: 发布者删除 removePost()
    A --> [*]: 发布者删除 removePost()

    note right of B
        标记后：
        · 列表中置灰并沉到后面
        · 详情页不再展示联系入口
        · 仍然可以被搜到（只是置灰，不是消失）
        · markDone 是幂等的，重复点不会
          改动原有的完成时间
    end note
```

## 图 4：认领验证（核心机制）

这张图里有四个地方是**特意**设计的，也是这一版与"第一版想法"的区别所在。

```mermaid
flowchart TD
    subgraph Publish["发布阶段（拾得者）"]
        P1[选类型：招领] --> P2{该分类有客观特征吗?}
        P2 -->|有 · 七类| P3[必须出 3~5 道客观题]
        P2 -->|无 · 「其他」类| P4[不出题 · 走信任模式<br/>描述与联系方式直接公开]
        P3 --> P5["只允许判断题 / 选择题<br/>判断题选项固定为「正确/错误」<br/>选择题选项由数据层重排下标"]
        P5 --> P6[保存：questions 里含 answer]
        P4 --> P7[保存：questions 为空]
    end

    subgraph View["浏览阶段"]
        P6 --> V1[详情页]
        V1 --> V2{访问者是发布者本人?}
        V2 -->|是| V3[看到完整联系方式 + 管理按钮]
        V2 -->|否| V4["🔒 联系方式为空串<br/>（不是被藏起来，是没进页面）<br/>姓名打码：周**"]
        V4 --> V5["显示：出了 N 道题<br/>剩余作答次数 M / 3"]
    end

    subgraph Claim["认领阶段（认领人）"]
        V5 --> C1[点「开始认领验证」]
        C1 --> C2["startClaim()<br/>一次下发全部题目<br/>只含题干与选项"]
        C2 --> C3[一次选完全部题目<br/>只有点选项，没有自由文本]
        C3 --> C4{全部答完了吗?}
        C4 -->|否| C5["提示「还差 N 道题」<br/>★ 不消耗次数"]
        C5 --> C3
        C4 -->|是| C6["submitClaim(answers)<br/>全员比对下标"]
        C6 --> C7{全部答对?}
        C7 -->|是| C8["✅ 解锁联系方式<br/>生成凭证码 CL-YYYY-XXXX<br/>★ 答对不消耗次数"]
        C7 -->|否| C9["❌ 只回「回答的细节与描述不符」<br/>★ 不告诉是哪一题错<br/>扣一次次数"]
        C9 --> C10{attemptsLeft == 0?}
        C10 -->|否| C3
        C10 -->|是| C11[解锁申诉入口]
    end

    subgraph Appeal["人工审核阶段"]
        C11 --> A1["申诉表单：称呼 + 联系方式<br/>+ 只有物主才知道的细节"]
        A1 --> A2[落到这条信息的 appeals 里]
        A2 --> A3["发布者在「我的发布 → 人工审核」查看<br/>（明细只有发布者能调 listAppeals 看到）"]
        A3 --> A4{发布者判断}
        A4 -->|同意交还| A5["解锁 + 生成线下交接编号"]
        A4 -->|驳回| A6["附一句理由回给申诉人<br/>联系方式保持锁定"]
    end

    style C5 fill:#fff8e6,stroke:#ffe1a3
    style C8 fill:#e6f7f2,stroke:#a8e3d3
    style C9 fill:#fdecee,stroke:#f6c9ce
```

### 图里四个"特意"的地方

| # | 设计 | 如果不这么做会怎样 |
| --- | --- | --- |
| 1 | **题型只有判断和选择** | 判定退回字符串比对，「深蓝 / 藏青」这类措辞歧义会把真失主拦在门外，而且"宽容到什么程度"没有正确答案 |
| 2 | **一次性作答 + 统一判定** | 逐题反馈等于给冒领者递排除法的线索，3 次机会足够把答案试出来 |
| 3 | **次数上限写进数据层** | `attemptsLeft` 存在信息上、扣减只发生在 `submitClaim()` 内部，绕过界面直接调数据层也躲不开 |
| 4 | **3 次用完才解锁申诉** | `canAppeal` 由"剩余次数是否为 0"推导，认领页、结果页、详情页三处按钮都以它为准，不会出现"提前出现申诉入口" |
